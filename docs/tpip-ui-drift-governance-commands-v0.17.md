# TPIP UI 漂移治理受控命令 v0.17

## 1. 目标与边界

v0.17 在 v0.14～v0.16 的只读评估、提醒资产和可回滚浏览器门禁之上，打通本地单用户场景的受控写链路：

1. 将可治理漂移报告物化为不可变策略快照驱动的执行账本；
2. 由服务端筛选已到期、预算未耗尽且未被活动批次占用的账本；
3. 创建 DRAFT 批次，并执行批准、取消、替代和提交；
4. 只有提交动作创建 Outbox，UI 不把“已批准”等同于“已发送”。

本阶段仍不引入登录、OIDC/JWT 或 RBAC。命令通过 `X-Operator` 记录本地操作人，默认值为 `local-ui`；认证与权限体系继续作为未来多用户或外部 Auth 环境接入项。

## 2. 服务端资格查询

新增 Workspace 作用域查询：

```text
GET /control/v1/verification-drift-workbench/governance-executions:due
    ?workspaceId={id}&limit={1..100}
```

查询只返回同时满足以下条件的执行账本：

- 状态为 `READY`；
- `nextReminderAt` 已到期；
- `reminderCount < maximumReminders`；
- 不存在 `DRAFT` 或 `APPROVED` 批次成员占用；
- 属于请求中的 Workspace。

资格判断由持久化查询和命令服务共同负责，前端不根据页面已有数据推断可执行性。命令提交时仍会再次校验，以抵御页面停留期间的状态变化。

## 3. 命令模型与副作用边界

### 3.1 冻结执行账本

治理评估页对尚未物化的候选提供“冻结账本”。用户确认后，服务端基于当前有效策略和评估结果生成执行账本，保存策略来源、负责人、聚合键、提醒预算、评估 checksum 和物化证据。同一漂移报告重复提交由服务端保持幂等。

### 3.2 创建 DRAFT

提醒批次页只展示服务端返回的到期候选。用户选择同一聚合组和负责人下的账本、检查环境编码并明确确认后，创建 `DRAFT`。该动作只建立成员预留，不创建 Outbox，也不代表通知已发送。

### 3.3 批准与取消

- 批准：`DRAFT → APPROVED`，不创建 Outbox；
- 取消：允许状态由服务端状态机决定，必须填写原因；进入 `CANCELLED` 后释放成员占用；
- 两者均携带当前 `rowVersion`，并在成功或冲突后刷新服务端状态。

### 3.4 原子替代

替代操作预填原批次成员，要求填写原因、新环境和执行账本 ID。服务端重新校验成员资格、聚合键和负责人，在同一事务中取消原批次、创建新 `DRAFT`，并建立 `replacedBy/replaces` 双向血缘。任一条件不满足则整体失败关闭，不留下半完成状态。

### 3.5 显式提交与 Outbox

提交是本阶段副作用最高的动作，因此对话框同时要求：

- 展示“将创建 Outbox，但不保证渠道已送达”的风险说明；
- 用户勾选显式确认框；
- 使用当前 `rowVersion`；
- 服务端再次校验状态、成员 checksum、提醒序号、到期时间与预算。

校验通过后，批次状态更新、提醒预算占用和 Outbox 创建在同一事务完成。Worker 的路由和渠道投递是后续异步过程；`PENDING/UNROUTED` 是合法的提交后状态，不应被 UI 解释为已送达。

## 4. UI 交互约束

- 所有写操作均先显示影响范围和状态警告；
- 取消、替代必须填写治理依据；
- 替代成员在对话框首次打开时立即预填，避免无意创建空替代批次；
- 提交必须额外勾选显式确认；
- 命令进行中禁用重复提交，完成后统一刷新评估、到期候选、批次详情和运营指标；
- 后端拒绝信息原样进入页面错误态，不能用前端逻辑绕过状态机。

## 5. 浏览器端到端验收

验收使用 `e2e/ui-governance-workbench` 创建独立 Workspace，并在 Control Plane `18082`、UI `18100` 下真实执行：

- 未物化候选 → 冻结执行账本；
- 到期账本 → 创建 DRAFT → 批准；
- 提交确认框未勾选时被 UI 拦截；
- 显式确认后提交，生成 `PENDING/UNROUTED` Outbox，未伪造渠道投递成功；
- DRAFT 取消后成员占用释放；
- DRAFT 原子替代后展示双向血缘和成员差异；
- 替代批次取消后，到期账本重新进入候选集合。

首轮验收暴露并修复了两个问题：替代对话框首次挂载未立即预填成员；夹具的 DRAFT 成员时间与服务端到期规则不一致。后者曾被服务端状态机正确拒绝，修正夹具时间后完整链路通过。两轮验收数据均执行 `cleanup` 与 `verify-clean`，端口也已释放。

## 7. 后续建议

v0.18 建议优先将命令审计时间线纳入提醒批次详情：按批次聚合创建、批准、取消、替代、提交证据，展示操作者、原因、请求 checksum、版本变化和 Outbox 关联。完成可视化审计闭环后，再把本次人工浏览器场景固化为可重复的自动化回归。
